# Dispatch API contract used by staff frontends

`lms-dispatch.swagger.v1.json` is a snapshot of the `LMS.Dispatch.Api` document served by the LMS gateway at `/openapi/dispatch.json`. The OpenAPI patch version is normalized from 3.0.4 to 3.0.3 for the project toolchain; the snapshot is maintained alongside the current API contracts.

`LMS-User` consumes the staff coupon, vehicle, shift, driver, and dispatch-order paths. `LMS-UserApp` consumes the staff dispatch-order paths. Driver-scoped paths in the same upstream document belong to `LMS-DriverApp` and are not staff frontend calls.

The monthly roster uses `GET /api/dispatch/staff/v1/shifts/calendar?from=2026-10-01&to=2026-10-31`, with an optional `propertyId`. Both dates are inclusive and required; the range must contain 1–31 business dates. The success envelope contains an array of daily boards in date order, including empty dates and all three periods. Property authorization, shift ordering, and `Cache-Control: no-store` match the daily board. The server queries shifts for the range once, joins current driver properties in that query, and loads distinct driver names in one batch. Edits refresh only the affected daily board.

## Current driver property and vehicle

Shifts store neither a property ID nor vehicle data; batch results store no property ID. Single creation accepts the driver, date, period, status and role; any legacy propertyId input is ignored. Read responses retain a read-only propertyId derived from the current driver record. Calendar filters, permissions, per-driver search/sort, reporting sources and withdrawals all use that current property. A driver transfer moves all of their shifts into the new property scope, including historical shifts. Old propertyId fields are ignored on reads and omitted by all new writes; no historical data cleanup is executed by the application.

Driver vehicle binding uses assignedVehicleId. The target vehicle must belong to the current driver property; application validation and transactional persistence both enforce this. A property mismatch returns HTTP 400 / code 40001 on assignedVehicleId with "The vehicle and driver must belong to the same property." Staff driver editors display this field message in the selected language and keep the form open. The roster reads the vehicle by current assignedVehicleId and supports legacy vehicle.driverId links only when that ID is absent. It returns a vehicle plate only if the vehicle belongs to the current driver property. Old shift vehiclePlate and vehicleSlot fields are ignored and omitted on writes. Driver binding changes affect all shifts, including history. The monthly query resolves property and vehicle in a single aggregation with indexed joins; no per-shift API calls are made.

The roster vehicle dialog patches the driver with assignedVehicleId, requires drivers:read and drivers:write, and explains that the change applies to all driver shifts. Legacy PUT/DELETE /shifts/{shiftId}/vehicle remain adapters to the same driver update workflow and require drivers:write; they never change shift documents or shift versions. The PUT input plate is only used to resolve a vehicle ID. New clients must use the driver PATCH endpoint.

## Batch scheduling

`POST /api/dispatch/staff/v1/shifts/batch-previews` computes a read-only preview. `POST /api/dispatch/staff/v1/shifts/batches` confirms it atomically. Both require `dispatch:write` and accept optional `propertyId` as a driver filter, unique `driverIds`, inclusive `from`/`to`, unique ISO `weekdays` (Monday = 1, Sunday = 7), `period`, `status`, and `role`. Ranges are limited to 31 calendar days and 1,000 driver-date combinations. Historical dates are supported. All selected drivers must be visible and active. If a property filter is supplied, every selected driver must currently belong to it; omitting it allows drivers from multiple visible properties.

The preview returns `previewHash`, driver/date counts, new/existing counts, `canSubmit`, and rows ordered by date and driver name/ID. Occupancy is queried only for the selected `period`. A driver can have morning, afternoon and night shifts on the same business date, but cannot have the same period twice, regardless of any legacy stored property. Existing shifts in the selected period are retained regardless of duty status or property; shifts in other periods do not block creation or appear in this preview. Visible existing rows contain their actual shift fields; inaccessible existing rows contain only the selected driver ID/name, date, and `isExisting`. Nullable shift fields are omitted when inaccessible; `shiftId` is also omitted for new preview rows. Invalid conditions return the standard 400/40001 error envelope instead of an incomplete preview. A fully occupied selection returns a valid preview with `canSubmit: false`.

Confirmation adds `previewHash` and requires `Idempotency-Key`. A changed preview or concurrent driver-date-period conflict returns 409/40900; the client must preview again. The hash covers normalized conditions, caller property scope, driver identity/eligibility and the selected dates' existing shift snapshots for the selected period. Changes to other periods do not invalidate this preview. The server re-reads drivers and global occupancy for the selected period inside the existing snapshot transaction, then bulk-inserts new shifts and their audit records, the persisted batch result, and the idempotency record. No existing shifts or driver vehicle bindings are updated. New shifts display the driver current bound vehicle at query time. A failed transaction creates no partial batch.

Successful confirmation returns 201/20100 with `batchId`, UTC `createdAt`, created/skipped counts and per-row results. Same-key same-body retries within the configured idempotency retention return the original persisted batch, even if drivers later change status. Reused keys with different bodies return 409. Results resolve property and driver names from the current driver records and are redacted against the caller's current property scope. Keep the same key and request body after a lost response, retryable server error, or exhausted rate-limit retry; the web drawer retains them while that preview remains unchanged. Batch responses use `Cache-Control: no-store`.

The schema is defined directly in `backend/migrations/scripts/20261022000200-ddl-dispatch-initial.js`: it creates `lms_dispatch.shift_batches` and the partial unique index `ux_active_driver_date_period` on `driverId`, `businessDate`, and `period` for records matching `withdrawnAt: null`. This includes legacy records without the field. Active shifts are unique per driver-date-period; withdrawn history does not occupy a period. The legacy `driverDateKey` field is retained for document compatibility but no longer has a unique index in the initial DDL. Single-shift and batch creation use the same rule. The batch collection's default `_id` index identifies persisted results. Batch results have no automatic expiry; the existing idempotency retention remains configured separately. There are no separate migrations for these scheduling features or a new background worker.

If a batch is blocked specifically by the legacy `ux_driver_date` index, the transaction rolls back and returns 503/50300 with `errors[].field = scheduling` and an administrator-action message. This is distinct from a changed preview (409 with `errors[].field = previewHash`); repeatedly previewing cannot resolve a missing schema migration. The web drawer displays the administrator-action message and clears the unusable preview.

The upstream shift board lists query names `Date` and `PropertyId`. The frontend sends `date` and `propertyId` to maintain the project camelCase wire convention; the .NET gateway binds query names case-insensitively. The upstream coupon request names a boolean `disabled` and overloads `faceAmount` as trips, percent, or MOP whole units. These deviations are confined to the Dispatch API adapter and form conversion. The upstream shift DTO uses `endsNextDay` rather than an `is`-prefixed boolean.

Contract tests cover route, method, query, request body, and idempotency-key mapping. Authenticated smoke tests require a staff bearer token and must be run against the gateway; no credentials are stored in this repository.

## Shift withdrawal

`POST /api/dispatch/staff/v1/shifts/withdrawals` requires `dispatch:write` and accepts `businessDate`, `period`, optional nullable `propertyId`, `isWholePeriod`, and 1–1,000 unique `targets` containing displayed `shiftId` and positive `version`. With `isWholePeriod: false`, exactly one target is required. With `true`, all active shifts in that date, period and authorized property filter must match the confirmed snapshot. Morning, afternoon and night are independent; this operation never withdraws another period. The roster exposes a withdrawal action on each driver card and a whole-period action in each period header, with a confirmation dialog showing date, period, property scope and count.

The server reads the confirmed targets in one snapshot transaction, validates scope and active versions, conditionally withdraws the active targets in one bulk write, and writes individual audit records. A stale version or changed period snapshot returns 409; missing or invisible targets return 404. Any failed conditional write rolls back the entire operation. Repeating already withdrawn target IDs is a no-op, even when new replacement shifts exist; retries cannot withdraw those replacements. New shifts created after the transaction snapshot are outside the confirmed target list and remain untouched. The 200 response contains `businessDate`, `period` and the count newly withdrawn by this request. Responses use `Cache-Control: no-store`.

Withdrawal retains scheduling fields, adds `withdrawnAt` (UTC) and `withdrawnBy`, and increments the version. It never changes the driver vehicle binding; no vehicle or vehicle occupancy key is stored on a shift. Active boards, calendars, driver lists, reporting sources, details and occupancy checks exclude withdrawn shifts. Original create-idempotency replays may still return the original historical shift. The staff page refreshes the month using the existing batch calendar endpoint after success. It supports Traditional Chinese and English and prevents duplicate submission or closing while submitting.

Withdrawal uses the same `ux_active_driver_date_period` index defined in the initial Dispatch DDL. The handler checks that this index exists and the obsolete full unique indexes are absent; otherwise it returns 503 with an administrator-action message and performs no withdrawal. The initial DDL describes the current schema for fresh initialization; editing an already applied version does not upgrade an existing database. Existing environments require a separately authorized schema and Flyway-history reconciliation, including the changed initial checksum and any previously applied migrations removed by this consolidation. This delivery does not modify database indexes, rewrite history or run Flyway repair/clean.
